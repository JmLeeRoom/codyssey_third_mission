## 1. 먼저 설명할 전체 처리 흐름

코드의 책임은 아래 순서로 분리한다.

1. `main`은 모드 선택, 입력 수집, 결과 출력만 담당한다.
2. 로더는 `size_3` 같은 크기 키와 레이블, 행 데이터를 파싱한다.
3. 검증 함수는 Grid의 크기, 정사각형 여부, 숫자 여부, `bool`/`NaN`/무한대 여부를 확인하고 정규화한다.
4. Grid 표현은 검증된 값을 2D 또는 1D 구조로 보관한다.
5. `mac`은 두 Grid의 같은 위치를 곱해 누적한 점수만 계산한다.
6. 판정 함수는 점수와 `epsilon` 규칙으로 레이블 또는 `UNDECIDED`를 결정한다.
7. 분석 함수는 예상 레이블과 비교해 `PASS`/`FAIL` 및 사유를 만든다.

이 분리는 입력/출력, 검증, 계산, 판정을 섞지 않기 위한 것이다. 특히 `mac`에는 파일 I/O, `print`, 시간 측정, 레이블 정규화를 넣지 않는다. 순수 계산 함수여야 단위 테스트와 성능 비교가 공정해진다.

### 1.1 필터 크기 키와 레이블 처리

예를 들어 JSON의 필터 키가 `size_3`, `size_5`처럼 들어오면 다음 순서로 처리한다.

1. 키가 기대 접두사 `size_`로 시작하는지 확인한다.
2. 접두사 뒤 문자열이 비어 있지 않은 양의 정수인지 확인한다.
3. 정수로 변환한 크기와 실제 Grid의 행/열 수가 같은지 검증한다.
4. 하위 필터의 레이블을 `+`, `cross`, `Cross` -> `Cross`, `x`, `X` -> `X`로 정규화한다.
5. 정규화 뒤 중복된 레이블은 조용히 덮어쓰지 말고 스키마 오류로 처리한다.

입력 Grid를 복사해 보관하는 설계는 외부 리스트 변경이 내부 Grid까지 바뀌는 별칭(aliasing)을 막기 위한 것이다. 다만 읽기 전용 데이터이고 소유권이 분명하다면 복사가 항상 필수는 아니다. 복사 비용은 MAC 성능과 별도로 측정한다.

### 1.2 새 레이블을 추가할 때의 확장 순서

`O` 같은 새 레이블을 지원하려면 하드코딩된 분기 하나만 추가하면 안 된다. 다음 순서로 확장한다.

1. 정규화 규칙과 입력 스키마를 확장한다.
2. 해당 레이블의 필터를 등록하고 크기를 검증한다.
3. 정상, 중복, 잘못된 레이블, 동점 사례를 테스트에 추가한다.
4. 모든 후보 필터의 점수를 계산하고 최고 점수를 찾는다.
5. 최고 점수 후보가 `epsilon` 범위에서 여럿이면 요구사항에 정의된 동점 정책을 적용한다.
6. 최종 레이블, 점수, `PASS`/`FAIL` 사유를 출력한다.

후보가 두 개인 현재 과제에서는 동점일 때 `UNDECIDED`가 명확하다. 후보가 셋 이상으로 늘어나도 반복 순서에 따라 임의의 1위를 고르면 안 된다. `UNDECIDED`를 유지하거나, 명시된 결정적 우선순위를 문서와 테스트에 함께 고정해야 한다.

## 2. MAC 점수와 판정

패턴과 필터가 같은 `N x N` 크기일 때 매칭 점수는 내적(dot product)이다.

$$
score = \sum_{r=0}^{N-1}\sum_{c=0}^{N-1} pattern[r][c] \times filter[r][c]
$$

각 위치의 곱을 누적하므로, 같은 크기의 이진 패턴과 고정 필터를 비교하는 과제에서는 점수가 클수록 겹치는 활성 위치가 많다고 설명할 수 있다.

다만 **일반적인 벡터에서 내적이 크다는 사실만으로 방향 유사도가 더 높다고 단정할 수는 없다.** 벡터의 크기(norm)가 다르면 값이 큰 벡터가 더 큰 내적을 만들 수 있기 때문이다. 방향 유사도를 말하려면 정규화한 뒤 코사인 유사도를 사용한다. 이 과제에서는 비교 대상의 크기와 표현이 고정되어 있으므로 `매칭 점수` 또는 `겹침 점수`라고 설명하는 편이 정확하다.

### 2.1 부동소수점과 `epsilon`

십진 소수 중 일부는 이진 부동소수점으로 정확히 표현되지 않는다. 곱셈과 누적 덧셈 뒤에는 아주 작은 반올림 오차가 생길 수 있으므로 점수를 직접 `==`로 비교하지 않는다.

현재 과제의 동점 규칙은 다음과 같이 절대 오차를 사용한다.

```python
EPSILON = 1e-9

if abs(cross_score - x_score) < EPSILON:
    prediction = "UNDECIDED"
elif cross_score > x_score:
    prediction = "Cross"
else:
    prediction = "X"
```

- 차이가 `epsilon`보다 작을 때만 동점이다. 요구사항이 `<`라면 `<=`로 바꾸지 않는다.
- `UNDECIDED`는 `Cross`나 `X`와 다르므로, 예상 답이 둘 중 하나인 JSON 테스트에서는 `FAIL`이다.
- 매우 큰 점수 범위까지 일반화하는 시스템이라면 절대 오차만이 아니라 상대 오차도 검토할 수 있다. 그러나 과제의 명시된 `epsilon` 정책을 임의로 바꾸면 안 된다.

## 3. 시간 복잡도와 측정값 해석

### 3.1 복잡도

필터 하나를 비교할 때 모든 위치를 한 번씩 방문하므로 정사각형 Grid의 MAC 시간 복잡도는 `O(N^2)`이다.

| Grid 크기 | 원소 수 | 3x3 대비 원소 수 |
|---:|---:|---:|
| 3x3 | 9 | 1.00배 |
| 5x5 | 25 | 2.78배 |
| 13x13 | 169 | 18.78배 |
| 25x25 | 625 | 69.44배 |

`5 x 5`의 전체 원소 수는 `25`다. 비교 필터가 `Cross`, `X` 두 개이면 패턴 하나를 판정하는 데 MAC을 두 번 수행하므로 총 곱셈 항 수는 `2N^2`가 된다.

원소 수를 `M = N^2`로 정의하면 MAC 하나는 `O(M)`이다. 따라서 "한 변의 길이 N에 대해 제곱으로 증가한다"와 "총 원소 수에 대체로 비례한다"는 같은 현상을 서로 다른 기준으로 표현한 것이다.

### 3.2 어제 측정한 비율의 설명

평가에서 언급한 기록은 3x3 기준으로 다음처럼 해석할 수 있다. 아래 실행 시간 값은 원본 측정 표의 구현 열(2D/1D)과 다시 같은 순서로 유지해야 한다.

| 비교 | 원소 수 증가 | 기록된 2D 실행 시간 증가 | 기록된 1D 실행 시간 증가 |
|---|---:|---:|---:|
| 3x3 -> 13x13 | 약 18.8배 | 약 15배 | 약 8배 |
| 3x3 -> 25x25 | 약 69.4배 | 약 55배 | 약 28배 |

측정 시간이 원소 수 증가율과 정확히 일치하지 않아도 `O(N^2)` 설명과 모순은 아니다. 작은 입력에서는 함수 호출, 루프 진입, 타이머 해상도 같은 고정 비용의 영향이 크고, 큰 입력에서는 캐시, CPU 주파수 변화, 메모리 접근, 운영체제 스케줄링의 영향을 받는다. 결론은 "완전히 비례한다"가 아니라 **원소 수 증가에 따라 대체로 증가하며, 관측치는 상수 비용과 실행 환경 때문에 흔들릴 수 있다**이다.

## 4. 2D Grid와 1D 평탄화 비교

2D Grid는 `values[row][column]`처럼 행 리스트와 열 인덱스를 거쳐 접근한다. 1D Grid는 모든 위치를 하나의 인덱스 공간으로 평탄화하고 다음 식으로 접근한다.

```python
index = row * size + column
value = values[index]
```

두 구현 모두 모든 위치를 방문하므로 시간 복잡도는 `O(N^2)`로 같다. 1D가 더 빨랐다면 이는 알고리즘이 더 좋기 때문이 아니라 다음과 같은 상수 비용 차이 때문이다.

- 2D는 바깥 리스트와 행 리스트를 차례로 참조한다.
- 2D `Grid.get()` 같은 추상화를 사용하면 메서드 호출과 경계 검사 비용이 핫 루프에 추가될 수 있다.
- 1D는 행 리스트를 다시 찾는 참조와 객체 경유를 줄이고 순차 접근 루프를 만들기 쉽다.
- 평탄화된 표현은 SIMD 또는 NumPy 같은 수치 라이브러리의 벡터 연산으로 옮기기 쉽다.

"1D의 모든 float 값이 물리 메모리에 완전히 연속해 있으므로 빠르다"라고 단정하지 않는다. Python 리스트는 객체 참조를 저장하며, 실제 `float` 객체의 배치까지 보장하지는 않는다. 더 정확한 설명은 **단일 리스트의 참조 배열을 순차 접근하고, 2D 행 리스트 및 메서드 경유를 줄일 가능성이 있어 구현 오버헤드가 작아질 수 있다**이다.

또한 현재 비교가 `2D Grid 클래스 + get()`과 `1D 일반 리스트`의 비교라면, 결과는 순수한 차원 표현만이 아니라 클래스/메서드 구조까지 포함한 구현 비교다. 어떤 요인이 큰지는 프로파일링 전까지 가설로 표현한다.

## 5. 공정한 벤치마크 방법

### 5.1 무엇을 측정할지 먼저 구분한다

| 지표 | 포함 범위 | 목적 |
|---|---|---|
| 순수 MAC 시간 | 검증을 마친 Grid에 대한 반복 MAC 호출 | 2D/1D 계산 구현 비교 |
| 전체 처리 시간 | JSON 로드, 검증, Grid 생성, MAC, 판정, 출력 준비 | 사용자 관점의 end-to-end 성능 |

I/O를 "측정할 수 없는" 것은 아니다. 다만 두 구현이 공통으로 한 번만 읽는 파일 I/O를 순수 계산 성능 비교에 섞으면 차이가 가려진다. 그래서 순수 MAC 시간과 전체 처리 시간을 별도 지표로 측정한다.

### 5.2 측정 절차

1. 같은 패턴, 같은 필터, 같은 반복 횟수로 2D와 1D를 비교한다.
2. `print`, 파일 읽기, JSON 파싱, Grid 생성은 순수 MAC 측정 구간에서 제외한다.
3. 함수 한 번의 시간이 너무 짧으면 MAC을 여러 번 반복하고 반복 전체의 바깥에서 타이머를 시작/종료한다.
4. 여러 샘플을 수집해 평균 또는 중앙값을 기록하고, 반복 수와 샘플 수를 표에 함께 적는다.
5. 측정 함수 내부의 MAC 루프마다 시간을 재지 않는다. 계측 호출 자체가 핫 패스에 추가되어 결과를 왜곡하기 때문이다.

Python에서는 `time.perf_counter()`가 짧은 구간 측정에 적합하다.

```python
from time import perf_counter


def measure_mac_time(mac_function, pattern, filter_grid, repeats=1_000):
    started = perf_counter()

    for _ in range(repeats):
        mac_function(pattern, filter_grid)

    return (perf_counter() - started) / repeats
```

이 함수는 후보 MAC 함수를 인자로 받아 같은 조건에서 비교한다. 실제 보고서에는 워밍업 여부, 반복 수, 샘플 수, 대표값(평균 또는 중앙값), 실행 환경을 함께 적는다.

## 6. 큰 입력에서의 최적화 방향

`1000 x 1000` Grid의 필터 하나는 약 100만 개 위치를 읽고 곱해 누적한다. 밀집한 일반 입력의 정확한 내적은 모든 원소를 확인해야 하므로, 알고리즘 차원에서 `O(N^2)`보다 작게 만들기 어렵다. 개선은 주로 상수 비용을 줄이는 방향이다.

1. Grid 평탄화는 로딩 단계에서 한 번만 하고, MAC 루프 안에서 재구성하지 않는다.
2. 핫 루프에서 불필요한 객체 생성, 깊은 복사, 메서드 호출을 줄인다.
3. 여러 필터/패턴을 묶어 처리해 초기화 비용을 분산한다.
4. 요구사항이 허용하면 NumPy 등 C 레벨 벡터 연산 라이브러리 또는 SIMD 구현을 사용한다.
5. 성능 시험의 반복 횟수는 충분한 측정 정밀도를 얻는 범위에서 정하고, 실제 서비스 처리량과 혼동하지 않는다.

1D 평탄화와 외부 수치 라이브러리는 서로 대체 관계가 아니다. Python 루프를 유지한다면 1D는 접근 비용을 줄이는 최적화이고, 수치 라이브러리는 내부의 C/SIMD 연산으로 루프 자체를 옮겨 더 큰 개선을 낼 수 있다.

## 7. CPU 직렬 처리와 NPU 병렬 처리의 병목

현재 Python의 중첩 루프 MAC은 기본적으로 CPU에서 직렬로 실행된다. 필터가 두 개이면 `2N^2` 위치의 곱셈-누적과 Python 인터프리터의 루프/인덱싱 비용이 발생한다.

필터별 점수 계산은 서로 독립적이므로, 병렬화한다면 필터 단위 또는 충분히 큰 행/인덱스 구간 단위로 나누는 것이 자연스럽다. 원소 하나마다 작업을 만들면 스레드 생성, 스케줄링, 결과 병합 비용이 계산보다 커질 수 있다. 작은 입력에서는 직렬 구현이 더 빠를 수도 있다.

NPU/GPU는 많은 MAC 유닛으로 여러 곱셈-누적을 병렬 실행할 수 있다. 그러나 유닛이 1,000개라고 CPU보다 정확히 1,000배 빨라지는 것은 아니다. 실제 병목은 다음에 의해 결정된다.

- 호스트 메모리와 가속기 사이의 데이터 전송
- 메모리 대역폭과 가속기 내부 메모리 접근
- 커널 실행 및 동기화 비용
- 너무 작은 배치로 인한 연산 유닛 미사용
- 결과를 다시 읽어 오는 비용

가속기를 사용할 때는 데이터를 한 번 전송한 뒤 여러 패턴/필터를 배치로 처리해 전송 비용을 나누는 편이 유리하다. 따라서 발표에서는 "NPU는 MAC 병렬성이 높지만, 실제 가속률은 연산량뿐 아니라 메모리 이동과 배치 크기에 제한된다"고 설명한다.

## 8. 평가 답변용 핵심 문장

- **왜 1D가 더 빠른가?** 두 방식의 복잡도는 같지만, 1D는 행 리스트 재참조와 `Grid.get()` 같은 추상화 비용을 줄일 수 있어 Python 핫 루프의 상수 비용이 작아질 수 있다.
- **왜 실행 시간은 원소 수 비율과 정확히 같지 않은가?** MAC 수는 원소 수에 비례하지만, 측정값에는 고정 호출 비용, 타이머, 캐시, CPU/운영체제 환경이 함께 반영된다.
- **왜 I/O를 제외했는가?** I/O를 측정할 수 없어서가 아니라, 공통 I/O가 순수 MAC 구현 차이를 가리기 때문이다. 전체 시간은 별도 지표로 측정한다.
- **왜 `epsilon`이 필요한가?** 이진 부동소수점 표현과 누적 연산의 반올림 오차 때문에 수학적으로 같은 값도 비트 단위로는 달라질 수 있어서다.
- **점수가 높으면 무조건 더 유사한가?** 이 과제의 고정된 이진 필터에서는 겹침 점수가 높다는 뜻이다. 일반 벡터의 방향 유사도는 정규화 또는 코사인 유사도가 필요하다.
- **병렬화하면 무조건 빨라지는가?** 아니다. 작은 작업에서는 분할/병합 비용이 더 크고, 큰 작업에서는 메모리 대역폭과 전송 비용이 속도를 제한한다.
